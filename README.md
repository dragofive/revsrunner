# custom-ios-runner

Отдельный репозиторий, который Codemagic клонирует для каждой iOS-сборки
пользовательского проекта в модуле Custom Builds (BYO). В отличие от
`ios-template` (фиксированная Capacitor-оболочка «сайт в приложение»), этот
раннер собирает СОБСТВЕННЫЙ проект пользователя: Flutter / React Native / Expo /
Capacitor / нативный Xcode.

Ничего специфичного для тенанта тут не хранится: исходники и Apple-ключ
приходят per-build через `environment.variables`, которые задаёт бэкенд RevsApp.
Один раннер обслуживает всех пользователей.

## Что делают воркфлоу

Три воркфлоу используют ОДНИ И ТЕ ЖЕ шаги сборки/подписи (через YAML-анкоры);
бэкенд выбирает нужный по `publish_target`:

- `custom-ios` (`publish_target = none`) - собрать подписанный `.ipa` и отдать
  на скачивание (без загрузки).
- `custom-ios-testflight-internal` (`publish_target = tf_internal`) - то же, что
  `custom-ios`, плюс загрузка в App Store Connect БЕЗ отправки на бета-ревью:
  сборка сразу доступна внутренним тестировщикам аккаунта.
- `custom-ios-testflight` (`publish_target = testflight`) - то же плюс
  `publishing.app_store_connect` с `submit_to_testflight`: загрузка `.ipa` и
  отправка в TestFlight beta review для внешних тестировщиков.

Внутренний вариант не задаёт ни `submit_to_testflight` (у Codemagic это поле по
умолчанию `false`), ни `expire_build_submitted_for_review` (оно управляет
очередью ревью, в которую сборка тут не попадает). Бета-ревью Apple нужно
только для ВНЕШНЕГО тестирования, поэтому одной загрузки достаточно: после
обработки сборка получает статус «Ready to Submit» и видна внутренним
тестировщикам. Подпись и сборка у всех трёх байт-в-байт одинаковые, так что тот
же `.ipa` можно потом продвинуть во внешнее тестирование без пересборки.

Воркфлоу `custom-ios-appstore` (`submit_to_app_store`) **удалён**: отправка
версии на ревью в App Store больше не предлагается как цель публикации. Для неё
нужны метаданные версии (скриншоты, описание, экспортная декларация, возрастной
рейтинг), которые может заполнить только сам тенант в App Store Connect. Сборка
уходит в TestFlight, а релиз в App Store тенант отправляет вручную. Бэкенд
отклоняет `publish_target=appstore` на уровне схемы, поэтому вернуть фичу одним
этим файлом нельзя.

Шаги (общие для всех трёх):

1. `scripts/download-source.sh` - скачивает ZIP исходников по `REVS_SOURCE_URL`
   (presigned) и распаковывает в `./src`.
2. `scripts/sign.sh` - получает/выпускает distribution-сертификат и профиль через
   App Store Connect API по ключу `.p8` тенанта, используя **постоянный**
   приватный ключ проекта (`CERTIFICATE_PRIVATE_KEY`, приходит от бэкенда).
   Профиль создаётся явно с РОВНО ОДНИМ id сертификата. **Без revoke** чужих
   сертификатов (автопилот, безопасно для аккаунта, которым пользователь
   подписывает и сам).
3. `scripts/build.sh` - prebuild по типу проекта (`flutter build ios` /
   `pod install` / `cap sync` / `expo prebuild`), находит `.xcworkspace`/
   `.xcodeproj` и схему, собирает `.ipa` и нормализует его в `build/ios/ipa/`.
4. `scripts/notify-backend.sh` - шлёт итог на `POST /api/custom/ios/webhook`,
   подписанный per-build HMAC-ключом (`REVS_WEBHOOK_TOKEN`). Отдельно про
   сборку и отдельно про публикацию, см. следующий раздел.

Загрузку/отправку делает встроенный публикатор Codemagic
(`publishing.app_store_connect`), а не CLI из скриптов (тот только подписывает).
Предусловие для publish-воркфлоу: приложение с этим Bundle ID уже создано в
App Store Connect.

## Два независимых вердикта: сборка и публикация

Раньше это был один статус, и сборка, которая СОБРАЛАСЬ, но не опубликовалась,
показывалась пользователю как полностью успешная. Теперь на вебхук уезжают два
независимых поля:

- `status` - только про сборку: `success` означает «подписанный `.ipa`
  существует», и ничего больше;
- `publish_status` - `not_attempted` | `success` | `failed`, про загрузку в
  App Store Connect.

Следствие, ради которого всё и делалось: провал публикации больше НЕ отнимает у
пользователя артефакт. Блок, который достаёт `secure_filename`, работает только
при `status = success`, поэтому раньше провалившаяся загрузка означала, что
бэкенд не получал имя файла, не скачивал `.ipa`, и пользователь терял сборку, за
которую уже списаны минуты.

Про причину провала уезжает МАШИННЫЙ КОД, `publish_error_code`, никогда не
текст. Русские формулировки собирает бэкенд. Правило жёсткое: пользователь не
должен узнать, какой CI-сервис собирает его приложение, и не должен видеть пути
сборочной машины, а дамп неудачного запроса к Apple вдобавок содержит живой
`Authorization: Bearer` от App Store Connect. Наружу уходят ровно два вида
значений: токен из фиксированного списка и строка цифр.

| Код | Когда | Откуда известно |
| --- | --- | --- |
| `appstore_build_number_duplicate` | Apple отклонила загрузку: такой номер сборки уже был (HTTP 409, `ENTITY_ERROR.ATTRIBUTE.INVALID.DUPLICATE` на `cfBundleVersion`) | дамп запроса; оттуда же берётся `previous_build_number` |
| `appstore_app_record_missing` | в App Store Connect нет записи приложения с этим Bundle ID | дамп запроса |
| `appstore_publish_failed` | загрузка не прошла, причину распознать не удалось | явный провал прогона при уже собранном `.ipa` |

Всё нераспознанное деградирует до `appstore_publish_failed`, то есть до общего
русского сообщения плюс напоминания, что артефакт доступен. Сырой текст не
уезжает никогда.

**Чего раннер знать не может.** Загрузка `.ipa` синхронна: она происходит внутри
прогона, до post-publish скриптов, поэтому её отказ мы видим. А ОТПРАВКА НА
БЕТА-РЕВЬЮ (вариант `testflight`) выполняется асинхронно, в post-processing уже
после завершения прогона, и статус этого шага обратно в сборку не приходит.
Именно так выглядела вторая реальная поломка: сборка попала в TestFlight, но не
ушла на внешнее ревью, потому что не была заполнена Beta App Review Information.
Из раннера это принципиально не видно. Поэтому `publish_status = success`
означает «загружено», а не «роздано тестировщикам»; узнать исход отправки можно
только опросом App Store Connect со стороны бэкенда. У `tf_internal` шага
отправки нет вообще, так что там «загружено» и есть весь путь.

## Разовая настройка

1. Создайте **приватный** GitHub-репозиторий (например `custom-ios-runner`) и
   запушьте туда содержимое этой папки (`codemagic.yaml` + `scripts/`). Никаких
   секретов тут нет.
2. В Codemagic: Applications → Add application → выберите этот репозиторий. Ключ
   доступа (`CODEMAGIC_API_TOKEN`) уже используется бэкендом, отдельный проект в
   UI регистрировать не нужно - бэкенд создаст Codemagic-приложение сам при
   первой сборке (дедуп по URL репозитория).
3. В `.env` бэкенда задайте:
   ```
   CUSTOM_IOS_RUNNER_REPO_URL=https://github.com/<you>/custom-ios-runner.git
   CUSTOM_IOS_WORKFLOW_ID=custom-ios
   CUSTOM_IOS_TF_INTERNAL_WORKFLOW_ID=custom-ios-testflight-internal
   CUSTOM_IOS_TESTFLIGHT_WORKFLOW_ID=custom-ios-testflight
   ```
   (все три переменные с workflow id имеют РОВНО такие дефолты, поэтому в `.env`
   их задавать НЕ нужно - только если переименуете воркфлоу в `codemagic.yaml`.
   В частности `CUSTOM_IOS_TF_INTERNAL_WORKFLOW_ID` добавлять никуда не надо.
   `CUSTOM_IOS_APPSTORE_WORKFLOW_ID`
   больше не существует - если он остался в старом `.env`, его можно удалить:
   настройки бэкенда игнорируют лишние ключи, так что сам по себе он ничего не
   ломает.)
   (переиспользуются существующие `CODEMAGIC_API_TOKEN`,
   `CODEMAGIC_WEBHOOK_SECRET`, `CODEMAGIC_INSTANCE_TYPE`). Пока
   `CUSTOM_IOS_RUNNER_REPO_URL` пуст, iOS-сборки custom-проектов отвечают 503
   (фича выключена).
4. Пересоберите бэкенд, чтобы `.env` подхватился.

## Подпись: один сертификат на проект (важно)

На проект приходится ОДИН distribution-сертификат, который переиспользуется во
всех сборках. Бэкенд один раз генерирует приватный RSA-ключ проекта, хранит его
зашифрованным и присылает в каждую сборку как `CERTIFICATE_PRIVATE_KEY`. Apple
привязывает сертификат к публичной половине ключа, поэтому `sign.sh` находит по
этому ключу уже выпущенный сертификат и ничего не выпускает заново. Новый
сертификат выпускается только если подходящего нет: первая сборка проекта, смена
Apple Team, истечение срока (за 7 дней до) или отзыв сертификата самим тенантом.

Раньше `sign.sh` генерировал ключ на каждую сборку, поэтому Apple выпускала новый
сертификат каждый раз; они копились и попадали в запрос профиля пачкой, а
App Store-профиль допускает ровно один distribution-сертификат - отсюда был
HTTP 500 от `POST /v1/profiles`. Поэтому: ключ постоянный И профиль создаётся
явно с одним id. `fetch-signing-files` не используется вообще (он подставляет в
профиль все сертификаты команды, и сузить этот список нечем).

Лимит активных distribution-сертификатов Apple публично не документирует, поэтому
**никаких чисел тут и в скриптах**. Если Apple отказывает в выпуске, сборка падает
с кодом `cert_create_failed`, и пользователь видит русское сообщение с действием:
освободить слот самому в Certificates, Identifiers & Profiles. Мы чужие
сертификаты не отзываем никогда (`app-store-connect certificates delete` в этом
репозитории не вызывается).

Профили - другое дело: свой собственный профиль с именем `RevsApp <bundle> <cert>`
скрипт может удалить и пересоздать, это обратимо и не трогает имущество тенанта.

## Переменные окружения и порядок деплоя

Бэкенд присылает их в `POST /builds` (полный список - в шапке `codemagic.yaml`).
Обязательные проверяются первым шагом воркфлоу; при отсутствии любой сборка
падает за десять секунд с `::error::Missing required env-var: <ИМЯ>`.

- `CERTIFICATE_PRIVATE_KEY` - постоянный приватный ключ подписи проекта. **Это
  секрет верхнего уровня**: кто им владеет, тот может подписывать софт от имени
  тенанта. Codemagic **не маскирует** переменные из `POST /builds` в логах
  сборки, поэтому защита тут только одна - дисциплина скриптов: никакого
  `set -x`, никакого `echo` значения, и только форма `@env:CERTIFICATE_PRIVATE_KEY`
  (в командную строку значение не попадает). `sign.sh` без этой переменной
  намеренно падает (`signing_key_missing`) и НЕ генерирует ключ сам.
- `BUNDLE_ID`, `TEAM_ID`, `APP_STORE_CONNECT_KEY_IDENTIFIER`,
  `APP_STORE_CONNECT_ISSUER_ID`, `APP_STORE_CONNECT_PRIVATE_KEY`,
  `REVS_BACKEND_URL`, `REVS_WEBHOOK_TOKEN`, `REVS_BUILD_ID`, `REVS_SOURCE_URL`.

**Порядок деплоя: сначала бэкенд (пересборка образа), потом push этого репозитория
в `revsrunner`.** Push - одна команда, бэкенд требует пересборки, так что удобный
порядок - неправильный. Если раннер уедет первым: старый бэкенд не шлёт
`CERTIFICATE_PRIVATE_KEY` (все iOS-сборки падают на первом шаге), и старый бэкенд
всё ещё отправляет `publish_target=appstore` в воркфлоу `custom-ios-appstore`,
которого тут больше нет - такая сборка умирает до запуска скриптов, вебхук не
уходит вообще, и строка сборки висит в `building` до таймаут-свипера.

**Для ДОБАВЛЕНИЯ воркфлоу порядок ОБРАТНЫЙ: сначала push раннера, потом
бэкенд.** Механизм тот же самый, просто повёрнутый другой стороной: Codemagic
резолвит воркфлоу из КЛОНИРОВАННОГО `codemagic.yaml`, поэтому если бэкенд
научится слать `custom-ios-testflight-internal` раньше, чем этот воркфлоу
появится в репозитории, сборка с новым таргетом умрёт до запуска скриптов,
вебхук не уйдёт, и строка будет держать слот конкурентности до свипера.
Обратный порядок безопасен: новый воркфлоу просто лежит неиспользуемым, id
существующих не менялись.

Одна оговорка на время окна между двумя шагами. Новый `notify-backend.sh`
докладывает провал публикации как `status = success` + `publish_status =
failed`, а старый бэкенд про `publish_status` ещё не знает и покажет такую
сборку просто успешной (то есть ровно как сегодня, хуже не станет) - но
артефакт при этом УЖЕ не теряется. Поэтому окно безопасное, но короткое: ставьте
бэкенд сразу следом.

Отдельно стоит знать: Codemagic подставляет `environment.variables` во ВСЕ шаги
воркфлоу, а `build.sh` выполняет чужой код из проекта тенанта (postinstall-хуки
npm/yarn, `expo prebuild`, `cap sync`, `pod install`, кастомные build phases).
То есть код проекта тенанта выполняется в окружении, где доступен ЕГО ключ
подписи и сохранённый `.p12`. Радиус поражения - один тенант в его собственном
Apple-аккаунте (ключи скоупятся на проект), но это стоит помнить, добавляя шаги.

## Окружение сборки: версия Xcode закреплена (с переопределением на сборку)

В `codemagic.yaml` на общем анкоре `&custom_ios_env` стоит `xcode: "26.6"`, а не
`latest`. Анкор один на все три воркфлоу.

**Зачем закреплено, и почему здесь это важнее, чем в конструкторе.** Этот раннер
компилирует СОБСТВЕННЫЙ проект тенанта (`build.sh` разводит flutter /
react_native / expo / capacitor / чистый ios) - ровно тот код, который мы не
можем починить, когда тулчейн уезжает под ним. На `latest` один переезд образа
на стороне провайдера ломает неизвестное подмножество тенантов разом, в коде,
который мы не имеем ни права, ни возможности править, и единственное
восстановление - push в этот репозиторий. Худший случай при этом даже не
красный билд: Apple требует UIScene lifecycle для любого UIKit-приложения,
СОБРАННОГО с SDK iOS 27, и проект, который его не принял, спокойно соберётся,
подпишется, загрузится и пройдёт обработку Apple, а потом упадёт на старте с
`UIScene life cycle is required for apps built with this SDK` (Apple TN3187).
Все сборки зелёные, все приложения не открываются, сигнала в CI нет нигде.

**Почему 26.6 и почему та же версия, что в конструкторе.** 26.6 - единственный
образ, подтверждённый реальной подписанной сборкой, доехавшей до TestFlight:
`Xcode-26.6.app` (17F113) на macOS 26.5.1 (билд 25F80), 23.09.2026. Одинаковый
образ в обоих репозиториях означает один срок жизни вместо двух и отсутствие
расхождений вида «в конструкторе подписывается, тут нет» поверх `sign.sh`,
который между репозиториями намеренно байт-в-байт одинаковый. Одно число
поднимать, одно число тестировать. `edge` не использовать никогда: он имеет
право быть бетой и сегодня это 27.0.

Это пин МИНОРА, не точной версии: патч-точное значение Codemagic сам резолвит в
последний патч этого минора, и на образах хранится один патч на минор. Нас это
устраивает: границы, которые мы морозим, мажорные.

**Что заставит поднять версию.**

1. Жёсткий срок, примерно апрель 2027: App Store Connect перестанет принимать
   загрузки, собранные не с SDK iOS 27 и новее.
2. Снятие образа 26.6 с пула. На `mac_mini_m2` неподдерживаемое значение
   `xcode` означает, что сборка НЕ СТАРТУЕТ вообще: скрипты не выполняются,
   `notify-backend.sh` не срабатывает, строка `CustomBuild` висит в `building`,
   держит слот конкурентности до таймаут-свипера и падает с неправильной
   причиной. Это та же молчаливая форма отказа, что описана выше в разделе про
   порядок деплоя. Прецедент даёт примерно месяц предупреждения.
3. Проект тенанта, которому действительно нужен Xcode 27. Этот случай НЕ
   требует трогать файл - см. переопределение ниже.

**Как поднимать безопасно.** Не менять значение «заодно». Сначала перевести
одну реальную сборку тенанта на новую версию через переопределение, убедиться,
что `.ipa` и загружается, И запускается на устройстве (зелёный билд про баг с
UIScene не доказывает ничего), потом менять значение по умолчанию и прогонять
минимум по одной сборке на каждый тип проекта, который поддерживает `build.sh`.
Значение держать в кавычках: без них это YAML-float, для 26.6 безвредно, но
будущее `26.10` молча прочитается как `26.1`.

**Переопределение на конкретную сборку.** Значение в файле - ДЕФОЛТ, а не
замок. Правильный тулчейн выбирает проект тенанта, а не мы: старый Flutter или
RN может сломаться на новом Xcode, а уже мигрировавший на scene стек может
наоборот хотеть 27, и ни то, ни другое не должно стоить push в этот
репозиторий. `POST /builds` принимает `environment.softwareVersions.xcode`,
который перебивает настройку воркфлоу; бэкенду достаточно НЕ слать это поле,
чтобы сборка приземлилась на пин, - именно так ведут себя все существующие
тенанты сегодня, так что переход ничего им не меняет. Со стороны бэкенда это
одно опциональное поле в `start_build` (`app/services/builds/codemagic.py`) и
его вызов в `app/services/custom/ios_build.py`. Вызов конструктора
(`app/services/builds/ios.py`) должен продолжать не слать ничего: та ветка
собирает нашу собственную оболочку и остаётся непереопределяемой НАМЕРЕННО.

Важная оговорка: приоритет `softwareVersions` над значением из
КЛОНИРОВАННОГО `codemagic.yaml` в документации прямо не описан (описан приоритет
над настройками UI). Пока это не подтверждено одной настоящей сборкой,
переопределение - операторское действие, а не фича в UI, и тенантам о нём
сообщать нельзя. Если приоритет окажется не тот, запасной путь - workflow input
(`${{ inputs.xcode }}` с дефолтом `"26.6"`), но ему нужна такая же проверка
одной сборкой: подстановка inputs внутри блока `environment` тоже не
документирована.

**Отдельно про `flutter: stable`** на том же анкоре: это тот же класс риска
(незакреплённая внешняя зависимость), и пин Xcode его НЕ закрывает. Flutter 3.41
сделал UIScene дефолтом и автоматически мигрирует подходящие приложения, то
есть переезд `stable` меняет результат сборки тенанта сам по себе. Это
отдельное решение со своей матрицей совместимости, сознательно не включённое в
эту правку.

## Заметки

- Это первый рабочий вариант. Реальные проекты разнообразны (монорепо,
  нестандартные схемы, кастомные `ExportOptions`), поэтому скрипты, скорее всего,
  будут дорабатываться по мере тестов на настоящих сборках - как и Android-движок
  отлаживался по стадиям на реальных сборках.
- Публикация в TestFlight включена в двух вариантах: внутренний
  (`custom-ios-testflight-internal`, без бета-ревью) и внешний
  (`custom-ios-testflight`, с бета-ревью). Факт ЗАГРУЗКИ теперь трекается
  отдельным полем `publish_status`, а вот итог РАЗДАЧИ (принято/на
  ревью/отклонено/роздано тестировщикам) в БД по-прежнему не трекается - ни у
  внутреннего варианта, ни у внешнего, как и в конструкторе. `publish_status =
  success` означает «загружено в App Store Connect», дальше смотрим в
  App Store Connect.
- Старые сборки в истории могут иметь `publish_target = appstore`: это история
  уже выполненных отправок, новые такие сборки создать нельзя.
